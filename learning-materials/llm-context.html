三、我的解释（个人化）

我把大模型的上下文理解成模型的"工作台桌面"：它每次回答问题时，能看见、能引用的一切东西都摊在这张桌上——你的问题、之前的对话、系统设定、工具说明书、临时贴上来的资料。

上下文窗口就是这张桌子的面积，以 token 为单位。桌子太小，材料放不下，模型"看不见"就等于"不知道"（这解释了为什么聊久了模型会忘记开头说过的话）；但桌子也不是越大越好——摊满一桌子的材料，找关键那页反而费劲。Anthropic 把这个现象叫上下文腐烂：token 越多，注意力被摊薄，准确回忆的能力反而下降。

所以高级的用法不是"把什么都塞进桌子"，而是只把当前最需要的高信号材料放上去，其余的收进抽屉（文件系统/知识库），要用再取——这就是从"提示工程"进化到"上下文工程"的核心思想。

四、核心机制 / 组成

上下文的组成典型内容作用
系统提示词角色设定、行为规范决定模型"以什么身份、按什么规则"工作
工具定义可调用工具的名称与说明告诉模型有哪些手可用（Agent 的关键）
对话历史多轮消息与工具调用结果任务目标与中间结果的"工作记忆"
外部注入资料RAG 检索片段、粘贴的文档补充模型训练时没有的知识

规模的直观感受：2023 年 Anthropic 把 Claude 的上下文从 9K token 扩到 100K——约 7.5 万个英文单词、几百页材料；一个人读完需要 5 小时以上，Claude 不到 1 分钟。官方演示中把《了不起的盖茨比》全文放入上下文，改动其中一行后模型仅 22 秒就找到了差异。但官方同时提示：对复杂问题，整篇放进上下文"很可能比基于向量检索的方法更好"——说明长窗口与检索是互补手段，不是替代关系。

五、具体应用场景

场景：本仓库的 Skill 就在管理上下文。concept-tutor Skill 并没有把"如何生成学习资料"的全部细节常驻塞进对话，而是当我说"学习概念 X"时才被加载（按需加载），且 SKILL.md 顶部只有一行 description 常驻——这正是"用最小的高信号 token 集合"原则的落地。再如：Agent 干活时循环多轮，工具输出越积越多；如果不做压缩，跑到后半程它可能"忘了"最初的任务要求——Anthropic 给出的对策包括压缩（总结后重启窗口）、结构化笔记（把关键决策写到窗口外的 NOTES.md，需要时取回）和子 Agent（让子 Agent 用干净窗口干活，只回传浓缩结果）。

我自己的体感验证：在长对话里让 AI"按开头说的格式输出"，它有时会走样——这就是上下文太长导致早期指令被稀释的日常例子。

六、容易混淆的问题与使用边界

❌ 上下文窗口 ≠ 记忆

窗口是"本次对话能看见的范围"，关掉会话就没了；模型没有跨会话的长期记忆，长期记忆要靠外部存储（文件、知识库、Skill）。

❌ 上下文工程 ≠ 提示工程

提示工程关注"怎么写好一段指令"；上下文工程是持续策划"哪些 token 应该进入模型视野"——范围覆盖系统提示、工具、历史、外部数据的整体管理。

  • 窗口大 ≠ 随便塞：注意力随 token 数增加被摊薄（Transformer 的注意力是 token 两两关系，n² 级增长），信噪比下降比"装不下"更早发生。
  • token ≠ 字数：一个汉字通常占 1~2 个 token，估算用量时要换算，不能按字符数直接想当然。
  • 使用边界：上下文适合放"当前任务必需"的信息；海量知识库应走检索（RAG）按需注入，而不是一次性灌入窗口。
